# 架构决策记录

## ADR-001：P1.1 登录限速不信任代理来源头

- **状态：** 已采纳
- **范围：** P1.1 HTTP 管理员登录

登录失败限速只使用 `http.Request.RemoteAddr` 中的对端 IP，不读取 `X-Forwarded-For`、`Forwarded` 或其他可由客户端伪造的代理头。

这样在未定义可信反向代理边界前保持保守默认值，避免攻击者伪造来源 IP 绕过限速。部署在反向代理后时，P1.1 看到的可能是代理地址，因此多个客户端可能共享同一限速桶。

后续部署阶段如需恢复真实客户端粒度，必须先明确可信代理列表，并仅由受信代理覆盖规范化后的客户端地址；不能直接信任任意请求头。

## ADR-002：前端状态管理使用轻量组合式 store，不引入 Pinia

- **状态：** 已采纳
- **范围：** P1.1 前端 `src/stores/`

P1.1 前端只有主题与认证两个跨组件状态。直接使用 Vue 3 `reactive`/`ref` 的模块级 store（`stores/theme.ts`、`stores/auth.ts`）即可满足需求；引入 Pinia 会增加依赖、样板代码和构建体积。若 P1.3 后状态复杂度上升（收藏、筛选、榜单缓存等），再评估迁移 Pinia，迁移成本限于 store 文件本身。

## ADR-003：生产容器内静态资源位于 `/app/public`，经 `STATIC_DIR` 传入

- **状态：** 已采纳
- **范围：** Dockerfile 与运行时配置

前端在独立的 Node 构建阶段产出 `dist/`，最终镜像复制到 `/app/public`；Go 服务通过 `STATIC_DIR=/app/public` 托管，数据库固定在 `/app/data`。这样二进制、静态资源、数据三者路径独立，健康检查与备份只关心 `/app/data`，也避免将静态文件嵌入 Go 二进制导致镜像层重建变慢。

## ADR-004：开发环境通过 Vite 代理联调，后端显式配置 `PUBLIC_BASE_URL`

- **状态：** 已采纳
- **范围：** 本地开发流程

`vite.config.ts` 将 `/api`、`/healthz`、`/readyz` 代理到 `127.0.0.1:8080`。登录和管理写接口校验 `Origin`，因此开发时后端需设置 `PUBLIC_BASE_URL=http://localhost:5173`（与 Vite 来源一致）。不在后端放开任意 Origin，也不为开发模式禁用 Origin 校验，避免两条环境行为分叉。

## ADR-005：P1.2 采集按时间窗口分片并逐页原子提交

- **状态：** 已采纳
- **范围：** GitHub 搜索采集与恢复

GitHub 仓库搜索最多只暴露 1,000 条结果，因此采集以 `created:<from>..<to> is:public` 时间窗口执行；当 `total_count > 900` 或 GitHub 报告结果不完整时递归二分窗口。每一页在同一事务内完成仓库 upsert、新仓库初始 Star 快照与下一页断点更新，进程中断后从已保存的 `next_url` 继续，而不是重跑整个窗口。无法继续拆分的窗口明确记为 `coverage_incomplete`，不能伪装成完整采集。

窗口的逻辑身份是 `(source, query_hash, time_from, time_to)`，分页进度 `page` 不是身份的一部分。迁移会先把旧约束允许产生的重复窗口按终态、分页进度和更新时间择优合并，并重定向事件及父窗口引用，再建立数据库唯一索引；这样分页推进后再次确保同一范围也只会复用原窗口。

窗口二分的终止条件是一分钟宽度下限，深度上限（20）只是安全网。真实 GitHub 每小时新增约 9,000 个公开仓库，七天回溯窗口要拆到约 12–14 层才会低于 900 条结果；固定的小深度上限（历史值 6）会在 2 小时 37 分的窗口上提前终止并把整段范围永久标记为 `coverage_incomplete`，该缺陷由真实 Token 验收发现并以“宽窗口在任意深度都必须继续拆分”的回归测试锁死。

## ADR-006：P1.2 Token 按 GitHub 数字身份共享冷却

- **状态：** 已采纳
- **范围：** GitHub 凭据与限流调度

添加 Token 时调用 `/user` 保存 GitHub 数字用户 ID，并以该 ID 作为额度身份。属于同一身份的多个 Token 视为共享额度组：其中任一 Token 对某个资源进入主/次限流冷却，整组在该资源上都不可用，禁止通过轮换同身份 Token 绕过 GitHub 限流。Token 仅以 AES-256-GCM 版本化密文保存，管理 API 只返回末四位提示。

## ADR-007：P1.2 定时任务使用数据库租约防止重复运行

- **状态：** 已采纳
- **范围：** 单实例当前实现及未来多进程兼容

调度器通过 `collector_jobs` 的 `lease_owner`/`lease_expires_at` 条件更新和 `RETURNING` 原子抢占任务。每次抢占生成包含进程角色和随机数的唯一 fencing token 写入 `lease_owner`，续租、释放和完成排期都必须携带该 token；因此即使多个执行器共用同一进程角色，过期后被接管的旧执行器也无法续租或清除新租约。租约有效期为 10 分钟；运行期间每 3 分 20 秒在同一事务中延长租约并更新 `job_runs.heartbeat_at`。续租不匹配时立即取消采集、将旧运行记为 `failed/lease_lost`（优先于同时出现的限流错误），且不能改写新 owner 的排期。运行成功或失败均条件释放租约，进程崩溃后可由过期租约恢复。手动运行与定时运行复用同一租约和 `job_runs`/`job_run_events` 记录，不建立第二套执行路径。

任务结束时在同一条条件更新中写入 `next_run_at` 并释放租约，避免先释放后排期导致另一个执行器在旧排期上重复抢占。GitHub 主限流或次限流记为 `deferred`，按 `RetryAt` 重排，不把资源配额问题计为仓库失败。

## ADR-008：详情同步与恢复补采使用独立配额和窗口命名空间

- **状态：** 已采纳
- **范围：** P1.2 仓库详情、Star 时间序列和覆盖恢复

增量 `github_collection` 每 30 分钟运行：先执行 Search 发现，再以独立的 `core` 配额客户端顺序同步一批到期公开仓库。详情 `200` 在一个事务中更新仓库并写 `repository_detail` Star 快照；`304` 只推进验证时间，不改 Star、不写快照；404/410 保留历史并降低检查频率。Search 观察到 Star 差异时只提前详情同步，不直接覆盖没有对应快照的当前值。

`github_recovery` 每 24 小时固定补采最近 48 小时，并使用 `github_recovery/created-public-recovery-v1` 窗口命名空间；增量游标只读取 `github_search` 窗口，因此恢复窗口不会跳过正常增量范围。失败窗口保存分页断点和指数退避时间，后续运行可按 source 重新领养；第三次失败转为显式 `coverage_incomplete`。父窗口标记 split 与两个子窗口创建在同一事务提交，避免崩溃后留下没有子窗口的 split 父窗口。

## ADR-009：P1.3 榜单增长口径与黑马分数

- **状态：** 已采纳
- **范围：** P1.3 排行榜（`/api/v1/rankings`）的 24h/7d 增长与潜力黑马榜

**决定：**

1. 净变化 = 每个仓库的「最新快照」减去「截止时间之前的最新快照」（基线）。没有基线的仓库直接不进入榜单，而不是拿 0 或当前 Star 填充——宁空不假。
2. `history_available` 只看增长窗口内是否存在早于截止时间的快照；为 false 时前端展示「数据不足」，`note` 字段给出解释。
3. 潜力黑马硬条件：创建 ≤ 30 天、总 Star ≤ 3000、近 7 天净增 > 0；分数 = 净增 × (1 + 描述 5% + 语言 3% + 话题 2%)，`score_reason` 输出可读解释。
4. 所有榜单统一 tie-break：`stars_count DESC, github_id ASC`，保证翻页顺序稳定；最新榜严格用 GitHub `created_at`，不用 `first_seen_at` 冒充创建时间。
5. SQL 侧排序表达式（`rankScoreExpr`）与 Go 侧 `calculateRankScore` 必须同步系数，代码注释互相引用。

**取舍：** 用窗口函数（`ROW_NUMBER() OVER (PARTITION BY repo_id ...)`）取基线与最新快照，比相关子查询可读，在当前数据量下性能足够；若快照表膨胀到千万级，再引入按 `(repo_id, captured_at)` 的预计算汇总表。
